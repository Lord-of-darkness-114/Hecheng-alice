# BLACK SOULS 版《合成大西瓜》双端方案

> 结论先行：**网页版和微信小程序版共用一套游戏核心（逻辑 + 物理），只有"画到哪块画布上、怎么读触摸"这两件事分成两个薄薄的适配层。** 物理引擎选 **Matter.js**，不选参考站点用的 Cocos Creator——原因见第 2 节。
>
> 已按此方案做了一个可运行的物理原型：`blacksouls-suika/prototype/index.html`，双击即可在浏览器里玩。第 5 节是实测结论。

## 1. 玩法定义（与《合成大西瓜》完全一致）

| 要素 | 设计 |
| --- | --- |
| 操作 | 顶部持球左右拖动，松手投放（微信端只允许横向移动，和原版一致） |
| 合成 | 两个**同阶**球碰撞 → 合成为下一阶，在被撞中点生成，给一点向上初速做"弹跳感" |
| 满级 | 最高阶不再合成，撞到只弹开 |
| 失败 | 任一球静止后仍高于警戒线，持续约 1 秒 → 结束。原版是"越线且停留"，不是"碰到就死"，这样手感和容错更好 |
| 计分 | 每次合成分数递增（1/2/4/8/…），最高分本地存档 |
| 投放池 | 只从最低的 5 阶里随机出（原版同款），避免一开局就出大球 |

**待你定**：阶数（建议 8 阶，和原版一致）和每阶对应的 BLACK SOULS 角色。

## 2. 技术选型：为什么不用参考站点的 Cocos Creator

我扒了参考站点的真实技术栈（`src/settings.c7aa8.json`）：

```
CocosEngine: 3.8.7 · 竖屏 720×1280 · physics.gravity.y = -20 · allowSleep = true
fixedTimeStep = 1/60 · maxSubSteps = 1 · 场景文件为二进制序列化
```

也就是 **Cocos Creator 3.8.7 + 内置 2D 物理（box2d）+ 精灵图集优化**，`gravity = -20` 且开了休眠——这套参数正好印证了第 5 节的调优方向。

它有它的道理，但对**我们这个项目**不合适：

| 维度 | Cocos Creator 3.8 | Matter.js + 自写渲染（推荐） |
| --- | --- | --- |
| 项目文件可读性 | 场景/预制体是二进制序列化，我无法直接改，必须靠你在编辑器里拖 | 纯文本，我可以直接读写 |
| 出包体积 | 引擎本身就有几 MB | 引擎 82 KB，整个游戏逻辑小于 100 KB |
| 双端一致 | 各平台各出一套构建产物 | 核心 100% 同一份代码 |
| 你要装的东西 | Cocos Creator（几个 GB）+ 微信开发者工具 | 只需微信开发者工具 |
| 贴图换装 | 得在编辑器里逐节点换 | 改 `assets/tiers/` 里的文件名即可 |
| 物理手感可控性 | 靠编辑器面板调 | 代码里就是几个明确的数字，可 A/B 实测 |

> 交付形态上还有个概念分叉，需要你选（第 8 节详述）：
> **微信小游戏** vs **微信小程序**。参考站点那个是网页版；如果你想在微信里"搜到就能玩"，小游戏的体验和性能都更好，小程序则更适合当"入口页"。

## 3. 代码架构（一套核心，两个壳）

```
blacksouls-suika/
├─ shared/                     ← 双端共用，纯 JS，零依赖（除 Matter.js）
│  ├─ config.js                阶数/半径/物理参数/配色/文案，美术换装只改这里
│  ├─ physics.js               引擎初始化、墙地、球体工厂、休眠策略
│  ├─ solver.js                穿透修正（本项目手感的关键，见第 5 节）
│  ├─ game.js                  投放/合成/计分/失败判定/连击
│  └─ render.js                画布绘制（背景→球→持球→特效→HUD）
├─ vendor/matter.min.js        物理引擎（网页端 <script>，小程序端 copy 进工程）
├─ prototype/index.html        已完成的物理原型（可玩、可调参、可测）
├─ web/                        网页版：index.html + adapter-web.js + assets
└─ wxgame/                     微信端：game.js + game.json + adapter-wx.js + assets
```

核心代码刻意用 **ES5 语法 + 不用 import/export**：

- 微信端：脚本按序执行，核心直接挂到适配层提供的全局对象上，**不需要打包工具**；
- 网页端：用同一份文件，靠 `<script>` 顺序加载，**双击就能跑**；
- 好处是"共享核心"不是口号，而是同一批文件被两端各自 include，改一处两端同时生效。

**适配层只需要实现 4 件事**（每端 100 行以内）：

```js
// 适配层接口
{ width, height, dpr }            // 画布尺寸与像素比
ctx                               // 2D 上下文
onDragStart(x) / onDragMove(x) / onDragEnd(x)   // 触摸
requestFrame(cb)                  // 帧驱动
emit(evt, data)                   // 音效 / 震动 / 分享 / 存档
```

这一层之所以薄，是因为**我不用 DOM 做游戏逻辑**——只用 Canvas 2D 的绘图 API，而微信的 `Canvas 2D` 接口是 W3C 兼容的（`drawImage` / `createLinearGradient` / `setTransform` / `save` / `restore` 全都有），官网明确推荐这条路，并且提供了 `canvas.requestAnimationFrame` 和 `SelectorQuery.node()` 拿到 `Canvas` 实例。所以"一次编写两端运行"在这个项目里是真的成立，不是勉强。

界面（按钮、分数、结算弹窗）我**也画在 canvas 上**，不用 DOM。这样两端连 UI 都不需要各写一套——代价是不能用 CSS 动画，但游戏 UI 本来就不该依赖 CSS。

## 5. 物理调优：我实测出来的问题和解法

> 这一节的关键结论来自一次对开源实现的专项调研（读了 Matter.js 源码 + 十几个
> 开源大西瓜仓库 + 官方 issue）。其中最颠覆的一条在下面第 6 点。
> **顺带纠正一个常见误解**：GitHub 上很有名的 `Degree-21/synthesis_watermelon`
> 并不是 Matter.js 项目，它是 Cocos Creator 2.x 导出到微信小游戏的产物
> （内置 Box2D），不能拿来学 Matter.js。

原型已经不是空谈，是真跑过的。用无头浏览器自动投放 15 秒、每秒采样所有球的位置，量化"球互相嵌进去多少"（圆心距小于半径和的超出量）：

| 配置 | 平均嵌入深度 | 深嵌球对数量 | 观感 |
| --- | --- | --- | --- |
| Matter.js 默认（6 次位置迭代） | **37.6 px** | 49 对 | 球堆糊成一坨，肉眼可见互相穿插 |
| + 位置迭代调到 10 | 仍在 10 px 级 | 明显减少 | 好转但不够 |
| **+ 几何分离修正（最终方案）** | **0 ~ 1 px** | 0 ~ 2 对 | 球面干净贴合 |

最终方案是这几项一起上（`shared/config.js` 的 `G.PHYSICS` 里都能调）：

1. **固定步长 1/60 秒 + 补步上限 5**：物理与显示解耦。高刷屏不会让物理跑快一倍，切后台回来不会瞬移炸开。
2. **全圆碰撞体**：圆的窄相检测是解析解，最快也最稳。
3. **休眠策略**（参考站点也开了这个）：静止球进睡眠，省 CPU 又消除堆叠抖动。
4. **参数**：`restitution 0.06`（低弹性）、`friction 0.42`、`frictionAir 0.008`、`slop 0.04`、`sleepThreshold 45`。
5. **位置迭代 10 次**：Matter 默认 6 次在球挤球时解不开重叠。**但别超过 20**——`Engine.update` 里有 `positionDamping = clamp(20 / positionIterations, 0, 1)`，到 1.0 后修正过激反而更抖。
6. **★ 渲染插值（"不够丝滑"的真正主因）**：物理固定 60Hz，屏幕可能是 120/144Hz，直接画物理位置会出现"同一位置连画两三帧"的台阶感。绝大多数开源实现都**没有**做插值（累加器余量 `alpha` 算出来了却没用于渲染），这就是"动画不够丝滑"的来源。我们按 `alpha = 累加器余量 / 步长` 在上一帧与当前帧之间线性插值。
   - **插值源必须是自己快照的 `prevX/prevY`，绝对不能用 Matter 的 `positionPrev`**：后者在 `Resolver.solveVelocity` 里被直接累加冲量、被 `postSolvePosition` 平移、被 `Sleeping.set` 重置，语义是"本步开始位置 + 求解修正"，不是上一帧渲染位置。拿它插值会看到细碎的抖。（这一条我第一版写错了，是调研时读源码才发现并改掉的。）
7. **关键一步——几何分离修正**：物理步之后，对仍然深嵌的球对做一次解析分离。

### 踩过的四个坑（都有自测用例守着）

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 用 `positionPrev` 做插值 | 高刷屏上细碎抖动 | 自己快照 `prevX/prevY` |
| 两球圆心完全重合时分离 | 除零放大，球被弹到 y=4843（场地外 3500px） | 重合时给确定性法线 + 单次修正上限 24px |
| 分离修正把球推进墙里 | 球越修越深，最后穿出场地 | 落地后做边界校验，会把球推出场地的修正直接撤销 |
| 地板只有 16px 厚 | 球单帧能走 20px，直接穿过地板 | 墙厚加到 80px（≥4 倍单帧最大位移）+ 速度上限 20px/帧 |

最后还加了一道 `contain` 兜底：万一有球跑出场地，贴回墙面并清掉朝墙速度。正常游玩永远不会触发（球是一个个从顶部掉的），但便宜且能防"这一局废了"。

### 关于帧率我要诚实说明

**无头浏览器 + 虚拟时钟环境下 `performance.now()` 会被冻结、`requestAnimationFrame` 不按正常节奏派发**，所以那里测出来的耗时恒为 0，截图也停在第一帧。我不想拿这种数字糊弄你。真机上的预期是：纯圆碰撞 + 20~40 个刚体 + Canvas 2D，中端手机 60fps 有充裕余量。

游戏里内置了诊断开关（`?debug=1`），会实时输出 `upf`（每帧物理步数，不是 1 就说明时间步不稳）、单次物理耗时、帧数、球数、穿透量。真机数据到手后我们按数据调。

### 原型自带的自测开关（也是我做回归测试的手段）

| URL 参数 | 作用 |
| --- | --- |
| `?auto=1` | 自动投放，无人值守压测/截图 |
| `?debug=1` | 每秒把全部球的坐标/速度/穿透量打到 console |
| `?stress=35` / `?stress=35&grid=1` | 一次性灌 35 球压测（`grid=1` 为网格摆放，负载更公平） |
| `?sep=0` / `?iters=6` | 关闭分离修正 / 改迭代次数，用来做对照实验 |
| `?perf=1` | 张开场地，只测引擎+渲染帧成本 |

## 6. 微信端要过的几道硬门槛（我已确认过）

| 门槛 | 现状与对策 |
| --- | --- |
| 主包体积 | 小游戏主包 4 MB / 小程序 2 MB。素材压缩后通常 1~2 MB，够用；超了就把高分辨率贴图丢分包 |
| 渲染方式 | 用 `canvas type="2d"`（小程序）或 `wx.createCanvas()`（小游戏），接口与 W3C 对齐 |
| 动画驱动 | 用 `canvas.requestAnimationFrame`，不用 `setInterval` |
| 触摸 | `wx.onTouchStart/Move/End`，坐标要按 `dpr` 和画布 CSS 尺寸换算（原型里这套换算已经写好） |
| 音频 | 小程序 `wx.createInnerAudioContext()`；注意 iOS 首次播放需要用户交互后触发 |
| 存档 | `wx.setStorageSync`，和网页版 `localStorage` 走同一个适配接口 |
| 分享 | `wx.shareAppMessage` 带战绩图片；这个在小游戏里是拉新的主力，建议做 |
| 上架 | 走微信公众平台注册 + 开发者工具上传 + 审核。**注意同人作品的版权/审核风险**：审核时避免直接使用原作名称、Logo 和角色原名，建议用你自己的角色命名体系。这条我会在命名上配合你 |

另外**性能优化三件套**：贴图全部**预生成到离屏 canvas**（避免每帧 `drawImage` 做缩放采样）、字符预渲染、静止时降低绘制频率。

## 7. 交付节奏（建议两步走，不要并行）

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| **第一步：网页版** | 接入你的贴图 → 完整玩法 → 特效/音效 → 手感调优 | 一个网址，手机浏览器直接玩，手感定稿 |

先做网页版的理由很实际：网页版改一行就能看效果，**手感调优需要反复试**，而小游戏每次都要走开发者工具预览，迭代慢十倍。手感在网页版定死之后，微信端只剩"接线"工作，风险小得多。

如果你希望两端同时看到东西，我也可以先出一版"网页版 + 微信工程骨架"，但微信端的手感调优仍然建议放到最后。
